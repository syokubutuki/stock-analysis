# 利用者数を増やすための方策

作成日: 2026-07-29
対象: https://stock-analysis-self.vercel.app

本書は「新しい分析を足す」以外の軸で、利用者数を増やす方策を整理する。
結論を先に書くと、**このサイトのボトルネックは分析の量でも質でもなく、
「見つからない・共有できない・初回で意味が分からない」の3点**にある。
244パネルはすでに過剰供給であり、次の投資先は流通と入口である。

---

## 0. 現状の事実（計測ではなくコードから確認できること）

| 項目 | 現状 | 出典 |
|---|---|---|
| クロール可能なURL数 | **5**（`/`, `/axioms`, `/portfolio`, `/strategy`, `/feedback`） | `app/sitemap.ts` |
| 分析画面のURL | **`/` 一本のみ**。銘柄・セクション・パネルはURLに出ない | `app/page.tsx` は `"use client"`、`useSearchParams` 不使用 |
| 状態の保存先 | localStorage のみ（`sa:lastTicker` / `sa:section` / `sa:period`） | `app/page.tsx:1096-1134` |

| 初回訪問時の表示 | 検索窓＋セクション名のグリッドのみ。**データはゼロ** | `app/page.tsx` の `{!data && !loading && !error &&` ブロック |
| OG画像 | なし（`twitter.card: "summary"`、画像指定なし） | `app/layout.tsx` |

| 永続DB | Vercel Postgres が feedback で稼働中 | `app/api/feedback/route.ts` |

**この表から読める構造的問題:**

1. 244パネル分の情報のうち、検索エンジンが見られるのは **0パネル**。全部クライアントレンダで、しかもデータ取得後にしか存在しない。
2. 「7203のこの分析、見て」と**人に渡せるURLが存在しない**。共有がゼロなら口コミ係数もゼロで、流入は常に新規獲得コストを払い続けることになる。
3. 初回訪問者は「銘柄コードを知っている」かつ「エントロピーやDFAが何か知っている」ことを前提にされる。この二重の前提を満たす人だけが残る。

## 1. ファネルで見た診断

```
発見 ──→ 初回理解 ──→ 反復利用 ──→ 共有 ──→ 発見（ループ）
 ↑                                          │
 └──────────── 今ここが切れている ────────────┘
```

- **発見**: SEO面が5URL。検索流入は「株価構造分析」という一般名詞の完全一致以外ほぼ期待できない。
- **初回理解**: 空状態＋専門用語タブ。離脱の最大要因はここにあると推定される（未計測）。
- **反復利用**: ウォッチリストが端末ローカル。端末を変えると資産が消える。戻る理由が「今日のq提案」以外に日次では薄い。
- **共有**: URL共有が構造的に不可能。画像書き出しもなし。ループが閉じていない。

したがって施策は「**ループを閉じる → 入口を広げる → 中を磨く**」の順に効く。

## 2. 視点別の方策

### A. 発見される（SEO・構造）

#### A-1. 銘柄別の動的ルート `/t/[ticker]` を作る ★★★（最重要）
現状 `/` 一本を、`app/t/[ticker]/page.tsx` に展開する。

- `generateMetadata` で銘柄ごとの title/description を生成
  → 「トヨタ自動車(7203) の株価構造分析 — ボラティリティ・曜日効果・テイルリスク」
- **サーバー側で最小限の実測サマリーをHTMLに出す**（年率σ、最大DD、Hurst、曜日別平均リターン、直近の状態）。
  ここが空だと Google に thin content（中身のない量産ページ）と判定されて逆効果になる。**数千URL作るなら、各URLに固有の数字が本文として載っていることが必須条件**。
- 既存の `app/page.tsx` はクライアントのまま `<AnalysisClient initialTicker={...} />` として下にぶら下げればよい。localStorage 復元より URL パラメータを優先させる。
- `sitemap.ts` を TOPIX500＋米国主要銘柄＋主要投信で生成（500〜2000URL）。

**期待効果**: インデックス面が5 → 数千。「7203 ボラティリティ」「9984 曜日 アノマリー」等のロングテールを取りに行ける。
**コスト**: 中（既存を壊さず包む形にできる）。

#### A-2. 分析解説の独立ページ `/guide/[id]` ★★★
`AnalysisGuide` の中身は、すでにプロジェクト規約（`CLAUDE.md`）によって
「概要・数式・用語定義・比喩・読み方・投資判断への活用・注意点」の7点セットで書かれている。
**244本分の高品質な日本語解説記事が、クライアントコンポーネントの中に埋もれて検索エンジンに一切見えていない。**

これは新規執筆コストほぼゼロの最大の未利用資産である。

- まず利用頻度の高い上位20〜30分析だけを静的ページとして切り出す。
- 「DFA 株価 とは」「ハースト指数 計算」「PBO 過剰適合」「ウォークフォワード 検証」など、日本語で競合の薄いキーワードが多数ある。
- 各解説ページから該当パネルへの導線（`/t/7203#frac-rolling-hurst`）を張れば、記事→ツールの転換が起きる。

**コスト**: 小〜中（上位20本の手動移植なら小）。

#### A-3. 動的OG画像 ★★
`next/og` の `ImageResponse` で `/t/[ticker]` ごとにOG画像を生成。
銘柄名＋主要統計3つ＋ミニチャート。今はカードが文字だけで、SNS上のクリック率が実質捨てられている。
**コスト**: 小。**効果対コスト比が全施策中で最良。**

#### A-4. 構造化データ・canonical ★
- `WebApplication` の JSON-LD、用語ページに `DefinedTerm`、解説ページに `FAQPage`。
- 全ページに canonical（現在未設定。`/` と `/?ticker=` が並立すると重複扱いになる）。

#### A-5. 用語集 `/glossary` ★
セクション名（量子・フラクタル・エントロピー…）が検索意図と乖離している。
用語集を単独URLで持つと、専門用語検索からの入口になる。

### B. 共有される（ループを閉じる）

#### B-1. URL に状態を持たせる ★★★（最重要）
`?ticker=7203&sec=calendar&panel=cal-weekday-edge&period=1y&mode=logReturn` を
`history.replaceState` で反映し、読み込み時に復元する。

**これがないと、このサイトの発見（例: 「7203の週末ギャップはμ≈0だった」）を人に伝える手段が存在しない。**
X・ブログ・Slack・投資クラブでの言及がすべて「サイト名」止まりになり、深いページへの被リンクが一本も生まれない。SEOと口コミの両方をここが同時に殺している。

実装は `app/page.tsx` の既存 localStorage 復元ロジック（1096行付近）に
「URLがあればURL優先、なければlocalStorage」の分岐を足すだけで済む。
**コスト**: 小。**優先度は全施策中1位。**

#### B-2. パネル単位の画像書き出し ★★★
- Canvas2D パネル: `canvas.toDataURL()` で即実装可能。
- lightweight-charts: `chart.takeScreenshot()` が v5 に存在。
- 「画像をコピー」ボタン＋画像内にドメイン名を焼き込む。

X（旧Twitter）で個人投資家に届く形式は URL ではなく**画像**である。
画像に URL が焼かれていれば、リポスト経由の流入が発生する。
**コスト**: 小（共通ラッパーを1本作れば全パネルに展開可能）。

#### B-3. 「今週の1枚」自動生成 ★★
Vercel Cron（`vercel.ts` の `crons`）で週次バッチを回し、
主要指数について「今週いちばん外れた指標」を1枚の画像＋2文の所見として生成し、`/weekly/[date]` に静的公開する。

- 投稿素材が自動で貯まる（＝発信の継続コストがゼロになる）
- 週次で更新される固有URLが増える（クロール頻度が上がる）
- 既存の `edge-decay`（SPRT+CUSUM）や `edge-ledger`（前向き台帳）がそのままネタ元になる

#### B-4. 埋め込み `/embed/[panel]` ★
ブログや note に iframe で貼れるようにする。被リンクが自然に増える。

### C. 初回で理解される（アクティベーション）

#### C-1. 空状態を廃止する ★★★
現状、初回訪問者は検索窓とセクション名の羅列を見る。**何も動いていない画面**である。
- デフォルト銘柄（日経平均 `^N225` かトヨタ `7203`）を即座に読み込んで表示する。
- 「まず何かが動いている」ことが初回離脱率を最も大きく変える。
**コスト**: 極小（`useEffect` の初期 ticker を設定するだけ）。

#### C-2. 「244パネル」を初回に見せない ★★★
セクションタブが18個、パネルが244個ある画面は、専門家以外には情報の壁に見える。
- 初回は **要約ダッシュボード5枚**だけ（現在値・年率σ・最大DD・今どのレジームか・今週の位置）。
- 「もっと詳しく」を押した人だけが18タブの世界に入る。
- これは既存機能を消す話ではなく、**既定の露出量を変える**話。

#### C-3. セクション名を目的語に変える ★★
「量子」「フラクタル」「エントロピー」は手法名であって、利用者の目的ではない。

| 現在 | 目的語ベースの案 |
|---|---|
| リスク・テイルリスク | 「どれだけ下がりうるか」 |
| カレンダー | 「いつ買って、いつ降りるか」 |
| エッジ | 「その優位性は本物か」 |
| 分布・非線形・量子 | 「値動きの癖を見る」（上級） |

手法名は副題として残せばよい。専門性は失われない。

#### C-4. 60秒ツアー ★
初回のみ、3ステップのハイライト（検索する→タブを選ぶ→ガイドを開く）。

#### C-5. モバイル・パフォーマンス ★★
298コンポーネントを `next/dynamic` で遅延読込しているとはいえ、
日中足の取得や重い計算がスマホで走る。LCP/INP を実測し、
初回表示に必要なパネルだけを先行読込する。**計測が先**（→ G）。

### D. 戻ってくる（リテンション）

#### D-1. 軽量アカウント ★★
ウォッチリストが localStorage のため、**端末を変えると資産が消える**。
Postgres はすでに稼働している（feedback で使用中）ので、
メールのマジックリンクだけの最小認証でウォッチリスト・パネル開閉状態・前向き検証台帳を同期できる。
前向き検証台帳（`edge-ledger`）は「凍結して未来のデータで採点する」設計なので、
**端末ローカル保存とは本質的に相性が悪い**。ここは機能的にもアカウントを要求する。

#### D-2. 週次メール ★★
「あなたのウォッチリスト銘柄で今週起きた統計的な異常」。
アカウントができれば自然に接続する。返ってくる理由を能動的に作れる唯一の手段。

#### D-3. 「今日のq提案」を日次の来訪理由に育てる ★★
`/axioms` の `TodayQProposal` は、このサイトで**毎日値が変わる唯一の画面**である。
- トップから常時見える位置に出す
- 「昨日の提案はどうなったか」の答え合わせを併記する（＝翌日も来る理由）

#### D-4. PWA ★
manifest を置いてホーム画面追加を可能にする。コスト小。

### E. 届ける（流入チャネル）

#### E-1. 「1分析1投稿」 ★★★
244パネル＝244本のコンテンツ在庫。X／note で1日1本、
「画像1枚＋3行の所見＋パネルへの直リンク」を投げる。
B-1（URL共有）と B-2（画像書き出し）が前提。

#### E-2. 反直観的な実測結果を前面に出す ★★★
このサイトの最大の差別化資産は、**「効かなかった」という検証結果を持っていること**。

- ヌル較正: エッジがゼロでも曜日最適化は **+279%** の累積リターンを出す（＝累積リターンには検出力がない）
- 週末プレミアム: ドリフトは平日夜間に集中し、**週末ギャップは μ≈0 で非有意**
- 個別ドリフトの識別限界: μ̂ は両端2点の恒等式であり、**観測頻度を上げても精度は改善しない**
- タイミング価値のSPA検定: 7203.T で p=0.334、**裏付けなし**

こういう結論は、他の株式情報サイトが構造的に出せない（読者が求めるのは「当たる話」だから）。
**「当てるサイト」ではなく「騙されないためのサイト」**という位置取りは、
日本語圏の株式Webで空白地帯である。これを看板にする。

#### E-3. 技術記事での流入（Zenn / Qiita）★★
- 「TypeScriptだけでSARIMAをWeb Workerで動かす」
- 「lightweight-charts v5 でマルチペイン時間軸同期」
- 「298コンポーネントのNext.jsアプリの構成」

投資クラスタとは別の母集団（フロントエンド・データ系）から流入する。
彼らは被リンクを書く母集団でもある。

#### E-4. 既存の動画資産との連動 ★★
`docs/` に資産形成YouTube動画の制作系（playbook＋テーマ100案＋台本）がある。
**動画側とサイト側が現状ほぼ分断されている。**
動画の各回テーマに対応するパネルへの直リンク（A-1・B-1でURL化されて初めて可能）を
概要欄に置けば、動画の視聴が丸ごと流入源になる。これは既にある資産の接続だけで済む。

#### E-5. コミュニティ ★
個人投資家の Discord・掲示板、大学の金融工学ゼミ、投資クラブ。
ただし「宣伝」ではなく E-2 の知見を持って行く形でしか通用しない。

### F. 信頼される（ブランド・法務）

#### F-1. 独自ドメインを取る ★★★
`stock-analysis-self.vercel.app` は、
(a) 覚えられない、(b) `-self` が不自然で怪しく見える、(c) `.vercel.app` はサブドメイン共有のため単独でのドメイン評価が積み上がりにくい。

**金融情報サイトで無料サブドメインは、それ自体が離脱理由になる。**
年1000〜2000円。効果対コスト比では A-3 と並んで最良。
（移行時は 301 と Search Console のプロパティ移行を忘れないこと。`sitemap.ts` の `BASE` と `metadataBase` も同時に更新する）

#### F-2. サイト名を固有名詞にする ★★
「株価構造分析」は一般名詞の連結で、検索でも記憶でも埋もれる。
E-2 の位置取り（騙されないための検定ツール）を表す固有名を付ける。

#### F-3. 運営者ページ ★★
金融ツールで運営者が不明なのは信頼上の欠落。
「誰が・なぜ・どういう方針で作っているか」を1ページ。
E-B（有意でなかった結果も出す）という方針の表明自体が差別化になる。

#### F-4. 免責は既に強み ★
`app/components/Disclaimer.tsx` の免責文は、多重比較・レジーム変化・標本期間の限界まで書いてあり、
一般的な株式サイトより明らかに誠実である。これを「隠すもの」ではなく
「私たちはここまで正直です」という**訴求点として前に出す**。

### G. 計測する（意思決定の土台）

#### G-1. カスタムイベントを入れる ★★★
現状 Vercel Analytics のページビューのみ。
**244パネルのうちどれが使われているのか、誰も知らない状態で開発が進んでいる。**

`@vercel/analytics` の `track()` で最低限これだけ:

| イベント | 目的 |
|---|---|
| `search_ticker` | 何を検索しているか（＝A-1 で優先生成すべき銘柄） |
| `section_change` | 18タブのどれが選ばれるか（＝C-3 の裏付け） |
| `panel_open` | 244パネルの利用率分布 |
| `guide_open` | 解説の需要（＝A-2 で先に切り出すべき記事） |
| `intraday_fetch` | 日中足の負荷（＝H-1 の見積り） |
| `watchlist_add` | アクティベーションの代理指標 |

#### G-2. ファネルを定義する ★★
`訪問 → 銘柄検索 → セクション切替 → パネル展開 → 再訪`
の各段の通過率を出す。C-1（空状態廃止）の効果はこの1段目で直接測れる。

#### G-3. 使われないパネルを畳む ★
利用率下位のパネルは、削除ではなく「上級」に隠す。C-2 の実行根拠になる。

### H. 供給側の制約（増える前に壊れないか）

#### H-1. Yahoo Finance 依存はスケール時の単一障害点 ★★★
`app/api/stock/route.ts` と `app/api/search/route.ts` は、
Yahoo Finance を認証なし・キャッシュなしで直接叩いている（投信は HTML から JWT を抜き出す実装）。

**利用者が増えた瞬間にレート制限・IPブロックで全機能が同時に停止する。**
つまり、集客施策の成功がそのままサービス停止の引き金になる。これは
「増やす前にやること」であって、増やしてから対処するものではない。

対策（順に）:
1. 日足に共有キャッシュを入れる（Vercel Runtime Cache、または Blob に日次スナップショット）。同一銘柄の10年日足は1日1回取れば足りる。
2. `/api/search` のサジェストを短TTLでキャッシュ（打鍵ごとに外部APIを叩いている）。
3. 主要銘柄（TOPIX500）は cron で日次プリフェッチしておく。A-1 のSSRサマリーもこれを読めば速い。
4. データ提供元の多重化（取得失敗時のフォールバック）。
5. 中長期では正規のデータ契約を検討する。ToS上の位置づけは、有料化するなら特に確認が要る。

#### H-2. 計算がクライアント側に寄っている ★
利用者が増えても自分のサーバー費用は増えないという利点はあるが、
低スペック端末での体感が悪いと C（アクティベーション）を直接損なう。
重い計算の Worker 化は SARIMA など一部で実施済み。上位パネルから順に広げる。

#### H-3. 有料化の順序 ★★
`/pricing` はすでにあるが、**分母がない段階での課金設計は早すぎる**。
無料利用者が十分に増えるまで、Pro は準備中のままでよい（現状の判断は妥当）。
なお `Disclaimer.tsx` に書かれた方針
（課金対象は「計算・可視化・保存」に限り、「今これを買え」と読める出力を壁の内側に置かない）
は法務上も妥当なので、有料化時も維持すること。

## 3. 優先順位（効果 × コスト）

| # | 施策 | 効果 | コスト | 優先 |
|---|---|---|---|---|

## 6. やらない方がいいこと

- **新しい分析パネルを増やす。** すでに244ある。245個目の限界効用はほぼゼロで、
  同じ工数を B-1 と C-1 に使ったほうが桁違いに効く。
  （新規開発を止めるという意味ではなく、**集客の手段として**は機能しないという意味）
- **有料化を先に作る。** 分母がない段階の課金設計は、答えの出ない議論に時間を溶かす。
- **多言語化。** 日本株＋日本語の解説という組み合わせ自体が現在の差別化。英語圏には強い競合が揃っている。
- **「当たる」方向への訴求。** このサイトの検証層（ヌル較正・SPA・PBO・前向き台帳）と正面から矛盾する。
  短期の流入は取れても、サイトの唯一の資産である「誠実さ」を失う。
- **一度に全部やる。** 上の優先順位は、後の施策が前の施策を前提にしている
  （H-1 なしの A-1 は障害を招き、B-1 なしの E-1 は投稿先がない）。順序を守る。
