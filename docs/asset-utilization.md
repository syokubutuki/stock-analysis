作成日: 2026-07-30
関連: [growth-strategy.md](./growth-strategy.md)（流通・集客の全体設計）

`growth-strategy.md` では「244パネルはすでに過剰供給で、次の投資先は流通と入口」と結論した。

各資産が何に生き、どういう機序で効くか**を書く。

新規開発を伴わない、あるいは伴っても既存物の接続で済むものだけを対象とする。

## 1. 作用の型は3つしかない

個々の活用案を並べる前に、**どう効くのか**の型を定義する。
以降の各資産は必ずこの型のどれかで説明する。型が言えない活用案は、やらなくてよい案である。

| 型 | 機序 | 効果の速さ | 複利性 |
|---|---|---|---|
| **(a) 面を増やす** | URL・記事・画像が増える → クロール対象と被リンクが増える → 検索流入 | 遅い（1〜3ヶ月） | 中（記事は減価しない） |
| **(b) 信頼を生む** | 検証可能な情報を出す → 離脱率が下がり再訪する → 転換 | 速い（即日） | 低（出しっぱなしで一定） |
| **(c) 時間が育てる** | 記録が積む → 後発が追いつけない → 参入障壁 | 極めて遅い（1年+） | **高（唯一の堀）** |

**最も価値が高いのは (c) で、このサイトは今まったく回収していない。**
そして (c) は「始めた日から時計が回る」ため、**着手の遅れがそのまま永久の損失**になる。
この非対称性が、本書で一番重要な指摘である（→ 2-6）。

## 2. 資産別の活用設計

### 2-1. AnalysisGuide 本文（約16,800行）— 面を増やす (a)

**なぜ未利用か**: `"use client"` のコンポーネント内 JSX にハードコードされ、
かつ折りたたみの中にある。クローラは実行もしないし展開もしない。

**何に生かすか（3方向）**

1. **解説ページ `/guide/[id]`**（→ growth-strategy A-2）
   `CLAUDE.md` の規約で「概要・数式・用語定義・比喩・読み方・投資判断への活用・注意点」の
   7点セットが282本すべてに揃っている。**規約が結果的にSEO用テンプレートとして機能していた。**
   - 作用機序: 「ハースト指数 とは」「PBO 過剰適合」「ウォークフォワード 検証 やり方」等の
     情報収集意図クエリ → 解説ページ着地 → 「この銘柄で実際に計算する」ボタン → ツール利用。
     **検索意図（学びたい）とツール（計算したい）の間の橋**が今は存在しない。
   - 実装の要点: 本文を JSX から**データに分離**する（`guides/[id].mdx` か構造化オブジェクト）。
     ここを飛ばして手写しすると二重管理になり、必ず片方が腐る。
   - **注意（重複コンテンツ）**: パネル内とガイドページに同一文が出ると自サイト内で重複する。
     ガイドページを正（canonical）とし、パネル内は要約＋リンクに縮める。
     副作用としてパネルUIも軽くなる（C-2 の「初回に見せすぎ」問題の緩和と同じ方向）。

2. **用語集 `/glossary`**
   「用語の初出時に日本語で意味を説明する」規約により、**用語定義が282箇所に散在している**。
   これを1ページに集約すると `DefinedTerm` の構造化データが作れる。
   - 作用機序: 単語検索（母集団が最大）→ 用語集 → 解説 → ツール。ファネルの最上流を取る。

3. **書籍・PDF 1冊**（→ 2-2 と合成）
   後述の系レジストリを章立てに、ガイド本文を各章の本体に使うと、書き下ろしゼロで1冊分になる。

**効果の見積り**: 面が5URL → 300URL級。ただし **A-1（銘柄別ルート）より先にやる価値がある**。
銘柄ページは「数字だけで文章がない」ため thin content 判定のリスクを常に抱えるが、
ガイドページは最初から本文が濃く、リスクがない。**低リスク側から面を作るのが順序として正しい。**

### 2-2. 系レジストリ `corollaries.ts`（1,720行・27系）— 信頼 (b) ＋ 面 (a)

**これは文章ではなくデータである**点が決定的に重要。
27の既存理論（CAPM・ケリー・…）が、5公準・5公理・5命題からの
**導出鎖（`DerivationStep[]`）として機械可読に**書かれており、
各系に `formulaTex` / `basis`（公準参照）/ `qChoice`（何の自由を最適化するか）/ `priority` が付いている。

**何に生かすか**

1. **JSON-LD の自動生成**
   データなので、系1つ＝1エンティティとして構造化データを機械的に吐ける。
   - 作用機序: 「CAPM 導出」「ケリー基準 証明」などの検索に対し、
     単なる本文ではなく**構造化された定義**として提示される → リッチリザルト適格性・AI検索での引用可能性。
   - 手書き記事と違い、27件を1つのテンプレートで生成できる（＝執筆コストゼロ）。

2. **「株式原論」を1冊のWeb教科書に**
   - 既存理論を**単一の会計恒等式 W = ∫q dP − C から全部導出した体系**は、
     日本語で無料公開されているものが事実上ない。
   - 作用機序（母集団の追加）: 現在の想定読者は「個別株の個人投資家」。
     教科書化すると **証券アナリスト/FP受験層・大学のゼミ・金融工学の学生**という
     まったく別の母集団が入口に立つ。彼らは (i) 検索で来る、(ii) **引用してリンクを張る**（被リンクは
     個人投資家層からはほぼ生まれない）、(iii) 相場に依存せず来る（＝相場が凪いでも流入が落ちない）。
   - `qChoice`（対象/符号/大きさ/タイミング/保有期間/配分）は
     **そのまま「あなたが今悩んでいるのはどの自由か」という診断UIの軸になる**。
     18セクションの手法名タブより、利用者の質問に近い（→ growth-strategy C-3）。

3. **`AxiomGraph` の依存グラフを共有画像に**
   27系の依存関係図は、それ単体で1枚絵として強い。X で最も拡散しやすい形式。

**注意**: `corollaries.ts` のコメントは「KaTeX 未導入のためプレーンテキスト」と書いているが、
`package.json` に katex は入っており `formulaTex` フィールドも存在する。
実装が追いついていないだけで、資産はすでに正しい形をしている（→ 2-9）。

### 2-3. 統計ライブラリ `app/lib/`（69,612行）— 面 (a) ＋ 信頼 (b)

**React依存はたった2ファイル**（`entitlement.ts`, `mu-mode-store.ts`）。
つまり実質すべてが**フレームワーク非依存の純TypeScript数値計算**であり、そのまま切り出せる。

自前実装している中身の例: SARIMA（Hannan-Rissanen 2段推定）・erf/gammaln/不完全ベータ・
行列反転・DFA/MF-DFA・移転エントロピー・コピュラ・GJR-EGARCH・Heston・Hill推定・
BOCPD・SSA・CCM・Cornish-Fisher・SPRT/CUSUM・Benjamini-Hochberg・ブロックブートストラップ。

**何に生かすか**

1. **npm パッケージ / GitHub 公開（コア部分のみ）**
   - 作用機序（二段で効く）:
     - **面**: 「TypeScriptだけで動く金融時系列の統計ライブラリ」は英語圏でも希少。
       GitHub star → Zenn/Qiita 記事 → **開発者が自分のブログから張る被リンク**。
       被リンクは個人投資家からは出ないが、開発者からは出る。**ドメイン評価はここで積む。**
     - **信頼**: 「計算コードが公開されている」＝ 数値を第三者が検証できる。
       このサイトの看板（→ 2-7 の「騙されないための」位置取り）に**技術的な裏付け**を与える。
       免責文で誠実さを主張するのと、コードを出すのは説得力の桁が違う。
   - **切り分けの判断**: 全部出すと差別化を失う。出すのは
     「検定・補正・推定の基礎層」（`stats-significance` / `unit-root` / `sarima` / `hill-estimator` 等）。
     出さないのは「エッジ探索と規律の組み合わせ層」（`edge-*` / `null-calibration` / `weekday-*`）。
     前者は教科書に載っている手法の実装で、隠しても優位性にならない。後者が固有の設計である。

2. **依存ゼロの証明として使う**
   外部の統計ライブラリに依存していないことは、
   「計算が壊れたら自分で直せる」＝継続性の担保として運営者ページに書ける材料になる。

### 2-5. コミット履歴（288件）— 信頼 (b)

コミットメッセージが日本語で、しかも結論を書いている。特徴的なのは**訂正の記録**:

- 「exceedanceのヌル3種で**前回の結論を訂正**」
- 「不完全ベータのバグ修正（小さい|t|でp過小）」
- 「μ の定義（対数/算術）を段階対応」
- 「免責を全ページに追加し、計算内容を超えた**タイトル・断定を正確化**」

**何に生かすか: 公開更新履歴 `/changelog`**

- 作用機序:
  - **信頼**: 「**自分の過去の結論を訂正した記録が残っているサイト**」は、
    株式情報の世界でほぼ存在しない。当てた話だけを残すのが業界の標準だからである。
    訂正履歴の存在自体が、他の主張の信頼性を担保する（訂正しない運営者は、
    訂正すべき時にも訂正しないと読者は推論する）。
  - **面と鮮度**: 更新されている固有URLが増え、クロール頻度が上がる。
  - **技術記事の種**: 「p値が過小になるバグを7ヶ月間出していた」という話は、
    統計を扱う開発者にとって読む価値のある記事になる（→ 2-3 の被リンク経路と合流）。

- 実装: `git log` から半自動生成。分析関連コミットだけ抽出すればよい。

### 2-6. 前向き検証台帳 `prospective-ledger.ts` — **時間が育てる (c) / 最優先**

> **2026-07-30 実装済（サーバー保存への移行）。** 設計と挙動は
> [`docs/prospective-ledger-server.md`](prospective-ledger-server.md) に分離。
> 以下は移行前の問題意識の記録として残す。残件は 12（`/track-record` 公開、最低1年待つ）。

これが**本書で最も重要な項目**である。

この台帳は「エッジを凍結日とともに固定し、凍結後に到着したデータだけで採点する」
臨床試験の事前登録に相当する仕組みで、ソース内でもそう説明されている
（「凍結後にパラメータを差し替えられないことが、この検証の価値の源泉」）。

**問題: 保存先が localStorage である。**

つまり——
- 端末を変えれば消える
- ブラウザのデータを消せば消える
- 運営側は誰が何を凍結したか一切知らない
- **1年後に「1年前に凍結した予測がどうなったか」という資産が、絶対に生まれない**

**この資産は「時間」しか材料にできない。後から作ることが原理的に不可能である。**
今日サーバー保存に切り替えれば1年後に1年分になるが、
1年後に切り替えたら、その時点でまたゼロから1年待つことになる。
**着手を1日遅らせるごとに、将来の資産が1日分減る。他のどの施策にもない性質。**

**何に生かすか**

1. **公開トラックレコード `/track-record`**
   運営者自身が主要銘柄について毎週エッジを凍結し、結果を自動採点して公開する。
   - 作用機序: 株式情報サイトの実績表示は、事後に選ばれた成功例か、
     検証不能なバックテストのどちらかである。
     **事前登録された全件（失敗も含む）が自動採点で並ぶページ**は、
     日本語圏の株式Webに存在しない。「なぜここを信じるか」という問いに対する
     唯一の構造的な答えになり、リンクを張られる理由になる（＝(a) にも波及）。
   - 失敗が並ぶことは弱点ではなく機能である。SPA検定で p=0.334（裏付けなし）を
     出しているサイトの一貫した態度として読まれる。

2. **利用者ごとの台帳（アカウント同期）**
   - 作用機序: 「凍結した予測の答え合わせ」は、**戻ってくる理由としてほぼ理想的**。
     時間が経たないと結果が出ないため、構造的に再訪を要求する。
     しかも待つ時間が長いほど価値が上がるので、乗り換えコストになる（＝リテンションの堀）。
   - Postgres はすでに動いているので、テーブル追加と最小認証だけで済む。

3. **`analog-ledger.ts` も同じ性質**を持つ。同時に移す。

**結論: この1項目だけは、他の施策より先に着手する理由がある。**
他は「早くやれば早く効く」だが、これは「遅れた分は永久に戻らない」。

### 2-7. 多重検定台帳 `test-registry.ts` ＋ Null result 群 — 信頼 (b) の最大値

`TEST_INVENTORY` は、アプリ全体で走る検定数を根拠つきで数え上げている
（例: 条件ペア交互作用スキャナ = 250検定、根拠「条件軸ペア×分位セル」）。
そこから **M·α（全エッジがゼロでも期待される偽発見数）** と
**1−(1−α)^M_eff（少なくとも1つ有意が出る確率）** を常設表示している。

**これは「自分のサイトの信頼性を自分から削る数字」を公開しているに等しい。**
そのような実装を、実際にやっているサイトを他に知らない。

そして実測された null result が揃っている:

| 結論 | 意味 |
|---|---|
| ヌル較正: エッジゼロでも曜日最適化は **+279%** | 累積リターンには曜日効果の検出力が**ない** |
| 週末プレミアム: 週末ギャップ **μ≈0 で非有意** | ドリフトは平日夜間に集中している |
| SPA検定: 7203.T で **p=0.334** | カレンダー戦略一族に経済的裏付けがない |
| 系C26: μ̂ は両端2点の恒等式 | **観測頻度を上げても個別ドリフトの精度は改善しない** |
| US×JP経路 4分析中3つ | null result |

**何に生かすか: サイトの看板そのもの**

- 作用機序（差別化が構造的である理由）:
  株式情報サイトの収益は「当たりそうな話」への期待から生まれる。
  したがって競合は **「効かなかった」を出すと自分の商品価値が下がるため、原理的に出せない。**
  この非対称性がある限り、「効かなかったことを検定して見せる」という位置取りは模倣されない。
  価格でも機能量でもなく、**インセンティブ構造による参入障壁**である。

- 具体的な使い方:
  1. **トップの1行**を「244パネル」ではなく「偽発見を数えるところから始める株価分析」に。
     機能量の訴求は、244も244も競合には数えられないので伝わらない。態度は1行で伝わる。
  2. **記事化**: 「エッジがゼロでも+279%出ました」は、
     個人投資家・データ分析者・統計クラスタの3つに同時に刺さる稀なタイトル。
     しかも**自サイトの機能を否定する内容**なので、宣伝臭がしない（＝拡散する）。
  3. **`M·α` を隠さずトップに出す**。「このサイトを全部使うと、
     エッジが本当にゼロでも期待して○件の"有意"が出ます」と自分から言う。
     これは自傷ではなく、**他のすべての主張の信頼を買う支払い**である。

- **注意**: この位置取りを取ると、「当たる」方向の訴求と併存できない。
  どちらかを選ぶ必要がある。併存させると最も価値のある資産が無効化される。

### 2-8. 投信データパイプライン — 面 (a)、母集団の追加

`app/api/stock/route.ts` は 7〜8桁の投信コードに対応し、
Yahoo!ファイナンスの HTML から JWT を抽出して BFF API を叩く独自実装を持っている。
個人開発ツールでここまで対応している例は少ない。

**なぜ未利用か**: `layout.tsx` の title/description/keywords に投信の語が一つもない。
sitemap にも投信ページがない。**能力があるのに、探している人に見つからない。**

**何に生かすか**

- 作用機序（母集団の桁が違う）:
  日本の個人投資家の多数派は個別株ではなく**投信・つみたてNISA層**である。
  「eMAXIS Slim 全世界株式 リスク」「オルカン 最大下落率」のようなクエリは、
  (i) 検索母集団が個別株より桁で大きく、
  (ii) 定量的な回答を返している競合が薄く（多くは商品説明とランキングのみ）、
  (iii) 検索者の意図が「怖い/大丈夫か」＝**このサイトのテイルリスク・最大DD・分布パネルの内容と一致する**。
- 具体的に:
  1. metadata の keywords/description に投信・NISA・積立を入れる（コスト極小）。
  2. A-1（銘柄別ルート）の生成対象で、**主要投信を個別株より優先する**。
     個別株ページは競合が厚いが、投信ページは空白地帯。
  3. 投信向けの入口ページを1枚（「あなたの積立商品はどれだけ下がりうるか」）。
- **相性の良さ**: 積立層は売買タイミングを探していないので、
  244パネルのうち「リスク・分布・相関ドラッグ」だけで足り、
  むしろ**初回に見せるものを絞る（C-2）方向と一致する**。

### 2-9. KaTeX（導入済み・使用は2/298）— 信頼 (b)

### 2-10. シグナルカタログ `edge-signals.ts` / ユニバース `universes.ts` — 信頼 (b)

- **`edge-signals.ts`** は「先読みバイアス回避: i日終値時点で確定する情報のみで建玉を決める」
  という契約を明示した名前付きシグナル群を持つ。
  - 生かし方: シグナル一覧を公開ページにする。
    作用機序 —「どういうルールで、どこで先読みを断ち切っているか」を公開すると、
    バックテスト結果の読み方が読者に伝わる。**数字を出すより、数字の作り方を出す方が信頼される。**
- **`universes.ts`** は「これは現在の主要銘柄リストであり、
  上場廃止・統合で消えた銘柄を含まない＝生存者バイアスあり」と自ら注記し、
  さらに point-in-time 診断が全銘柄生存を検出して警告する実装まで持っている。
  - 生かし方: **バイアス開示ページ**にまとめる。
    作用機序 — 生存者バイアスを自分から申告しているサイトは稀で、
    2-7 の看板を「1つの標語」から「複数の証拠物件」に変える。
    標語は真似できるが、コードに埋まった警告実装は真似のコストが高い。

### 2-11. 動画制作系（playbook＋100テーマ＋台本）— 面 (a)

- 作用機序: 動画は「見て終わり」だが、
  各回テーマ → 対応パネルへの直リンクを概要欄に置くと、動画1本が流入口になる。

## 5. 資産を殺す使い方（やってはいけないこと）

- **ガイド本文を手でコピーしてページ化する。**
  二重管理になり、必ず片方が腐る。データに分離してから1ソースで両方描く。
- **ガイド本文を AI で薄く増やして量産する。**
  現在の価値は「7点セットが全部埋まっている密度」にある。
  薄い記事を混ぜると thin content 判定でドメイン全体が沈む。**既存282本の質が担保**。
- **`app/lib` を全部OSSにする。**
  基礎層（教科書の実装）と固有層（エッジ探索と規律の組み合わせ）を分けずに出すと、
  差別化そのものを配ってしまう。
- **すでに無料で公開しているものを Pro の壁の内側に移す。**
  `Disclaimer.tsx` に書かれた方針（課金対象は計算・可視化・保存に限る）と、
  既存利用者の信頼の両方を壊す。壁は新機能で作る。
- **Null result を「でも実はこう使えます」と救済する。**
  救済した瞬間に、2-7 の差別化は消えて普通の株式サイトになる。
  効かなかったものは効かなかったと置いておくこと自体が商品。
- **設計書を運営者の持ち高込みで公開する。**
  投資助言との境界（`Disclaimer.tsx` の設計方針）に近づく。前提は一般化して出す。
- **公開トラックレコードを、データが溜まる前に作る。**
  1ヶ月分の記録は統計的に何も言えないうえ、
  「実績」と称して薄い数字を出すことは、このサイトが最も批判している行為そのものになる。
  **1（サーバー保存）を先にやり、12（公開）は最低1年待つ。** 順序が逆だと自己矛盾する。
