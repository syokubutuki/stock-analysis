## 手順

### 1. 何が変わったかを自分の目で確かめる

```
git -C ..\sa-s20 log --oneline main..HEAD
git -C ..\sa-s20 diff --stat main...HEAD
git -C ..\sa-s20 status --short        # 未コミットの取り残しが無いか
```

**diff を実際に読むこと。** コミットメッセージや実装セッションの報告を信用しない。
ラウンド4までに、計画書とコードの食い違いが5件見つかっている。**コードを正とする。**

### 2. コミットの順序を見る（★今回はここが効く）

S20 は「**1コミット目は棚卸し表だけ**（実装を1行も含まない）」を条件にしてある。
**`git log --oneline --reverse main..HEAD` を古い順に読み、
1本目が `docs/canvas-alt-text-inventory.md` だけであること。**
`git show --stat <1本目>` で確かめること。実装が混じっていたら、それは
「先に母数を出す」という条件の骨抜きである（§0.7① の再発）。報告すること。

第4波では、この検査で S19 の安全網テストが**確かに移設より前**にあることを確認できた。
順序は自己申告ではなくログで決まる。

### 3. 受け入れ条件を1つずつ検算する

§3 のプロンプトに番号つきで書いてある。**「満たした」という報告を信じず、自分で確かめる。**
確かめられないものは「確かめられなかった」と報告すること（満たしたことにしない）。

**過去の失敗の型を思い出すこと:**

- **§0.5③「数えた対象がそもそも不完全」** — 「N箇所直した」と書いてあったら、
  **その N の数え方自体を疑う。** grep の網に入らない表記が別にないか自分で引く
  （FU12 は2値で386箇所と数え、短縮表記65箇所を取りこぼしていた）
- **§0.7①「分母が出ていない」** — 棚卸しを求めた条件が満たされていないと、
  **他の条件も検算できなくなる。** S18 は Canvas 150件のうち10件だけ実装したが、
  150 という母数はレビュー側が数えて初めて出た。**分母を先に自分で数えること**
- **§0.7⑤「既存のテストが守っている」という主張** — **そのテストを開いて
  何をアサートしているかまで読むこと。** ファイル名は根拠ではない。
  S17 は「ticker-pages.test.ts が台帳を固定する」と書いたが、実際に固定していたのは
  1銘柄と件数下限の2点だけで、そのテストは main に元からあり1行も足されていなかった
- **FU18 の形** — 受け入れ条件を満たしたまま22節ぶん問題が残り、
  「確認済み」の中に埋もれていた
- **§0.6① の形** — 受け入れ条件が「数値で報告」でも、設計が変わって
  その測定が意味を失うことがある。**条件の文面ではなく意図を見ること**

### 4. 意味の整合を確かめる（★ 無衝突マージを信用しない）

```
git merge-base main feat/canvas-alt-text-rest
git log --oneline "$(git merge-base main feat/canvas-alt-text-rest)..main"
```

分岐後に main へ入った変更が触った**概念**を、作業ブランチ側でも grep すること。
第1波は3件とも無衝突マージだったが、`opengraph-image.tsx` が `range=1y` に
取り残されていた（§0.5①）。**「衝突しなかった」は「整合している」ではない。**

### 5. 今回の固有リスク（★ S20 用。波が変わったらここを書き換える）

**S20 の失敗は「棚卸しを出さずに一部だけやる」形で出る。** S18 がまさにそれで、
Canvas 150件のうち10件だけ実装し、**受け入れ条件を満たしたまま140件が残った**（§0.7①）。

**① 棚卸し表が第1コミットに単独で入っているか（★受け入れ条件1）**

`git log --oneline --reverse main..HEAD` の**1本目が `docs/canvas-alt-text-inventory.md` だけ**で、
実装を1行も含まないこと。含んでいたら条件1は未達である。

**② 母数の数え方の説明があるか**

プロンプトは母数を **2026-09-04 時点の実測**（`getContext("2d")` を持つ .tsx **152件** /
`<canvas` を持つ .tsx **176件**）で与えている。**この差分の説明が表の前に書かれていること。**
そして**自分でも数え直すこと**:

```
grep -rl 'getContext("2d")' app --include=*.tsx | wc -l      # 152 前後
grep -rl '<canvas' app --include=*.tsx | wc -l               # 176 前後
```

**この数字は波をまたぐたびに動いている**（第3波 150/173 → 第4波 151/174 → 現在 152/176）。
オーナーが幾何リターン層を並行して育てているためで、**前の波の数字をそのまま信じないこと**
（§0.8⑥・FU44）。**ずれていること自体は問題ではない。説明が無いことが問題である。**

**③ 棚卸し表の全件が「対応した / 対応不要」に決着しているか（★受け入れ条件2）**

表の行数と `AccessibleCanvas` の使用箇所を突き合わせること。

```
grep -rl 'AccessibleCanvas' app/components/analysis/*.tsx | wc -l
```

**残件が0でないなら、件数と理由が表に書かれていること。** 「優先度が低い」だけでは理由にならない。
**§0.7① と同じ「条件を満たしたまま大半が手つかず」を繰り返させないこと。**

**④ FU36 — 色と記号が同じ判定から出ているか（★ここが無言で残る）**

S18 は `DirectionGlyph` を184箇所に足したが `eps` を渡した箇所が**0件**だった。
色側には不感帯がある（勝率 0.48–0.52、`signShare`/`posShare` 0.4–0.6、`|ic|<0.1`、
`PersistenceChart` の相関）。**色が灰色なのに記号だけが方向を主張する。**

> **★ 素の grep で数えないこと。**
> `grep -rn 'DirectionGlyph' … | grep -c 'eps'` は、FU36 が未着手でも **1** を返す。
> `DirectionValue.tsx` の**定義側**（`eps = 0` の既定引数と内部の受け渡し）を拾うためである。
> 同じ理由で `<DirectionGlyph` の単純 grep は 185 を返すが、呼び出しは 184 である。
> **定義ファイルを除き、複数行にまたがる JSX も拾って数えること。**

```
node -e '
const fs=require("fs"),path=require("path");let g=0,ge=0,v=0,ve=0;
(function w(d){for(const e of fs.readdirSync(d,{withFileTypes:true})){const p=path.join(d,e.name);
 if(e.isDirectory()){if(e.name!=="node_modules")w(p);continue;}
 if(!e.name.endsWith(".tsx")||e.name==="DirectionValue.tsx")continue;
 const s=fs.readFileSync(p,"utf8");
 for(const m of s.matchAll(/<DirectionGlyph[\s\S]*?\/>/g)){g++;if(/eps\s*=/.test(m[0]))ge++;}
 for(const m of s.matchAll(/<DirectionValue[\s\S]*?>/g)){v++;if(/eps\s*=/.test(m[0]))ve++;}
}})("app");
console.log("Glyph",g,"eps",ge,"/ Value",v,"eps",ve);'
```

**マージ前の main での実測は Glyph 184 / eps 0・Value 36 / eps 0 である。**
**eps が0のままなら FU36 は未着手。** 数だけでなく、
**不感帯のある箇所で実際に閾値が一致しているか**を数件そのコードで確かめること。

**⑤ FU37 — 方向を持たない量から記号が外れたか**

最大ドローダウンは定義上つねに ≤0 なので **▼が常時点灯**していた（`VolTargetingChart` ほか3箇所）。
**σ・尖度・分散など方向を持たない量にも付いていないか**を、表の「今回の扱い」列で追えること。
差（`strat.maxDD - bh.maxDD`）は符号を持つので残ってよい。

**⑥ 描画方式が変わっていないこと（CLAUDE.md の規約）**

```

```

**マージ前の main（2026-09-04）での実測値は createChart 142 / getContext 175 である。**
**投入時に自分で数え直して、それを基準にすること。**
時間軸の図を Canvas2D に戻していないか、逆に非時系列の静的図を lightweight-charts に
置き換えていないか。**数が動いていたら理由を聞くこと。**

**⑦ 代替テキストが計算結果から生成されているか（固定文言でないか）**

**S15 のバッジと同じ内容を二重に読ませていないか**も見ること（§0.6③）。

**⑧ S19 の土台を壊していないか**

`app/lib/chart-colors.ts` は S20 の専有ファイルだが、**S19 がテストを張った**:
`app/lib/__tests__/chart-colors.test.ts` が `CHART_COLORS.ink` / `grid` を
`globals.css` の `@theme inline` と突き合わせている（FU29）。

- **色の定数を動かしたなら `globals.css` も動いていること**（片方だけなら二重管理が壊れている）
- `surface` は「相当」であって同値ではない。**一致しないこと**を固定しているので、
  そこを一致させたなら対応表も格上げされていること
- パネルを増減していないこと（`npm test` の golden・分類の内訳・seriesMode の比率が動く）

**⑨ 秒を測ること（§0.8① の教訓）**

第4波の退行は **test / lint / build が3方式とも通り、最終状態も同じで、
画面が固まる時間だけが7倍**という形で出た。S20 は Canvas を151件触る。
**代表的な重い節（calendar 56件）で「すべて開く」を押し、
main と作業ブランチで所要時間を両方測ること。** 報告の数値を受け取らないこと。
