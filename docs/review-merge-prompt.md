## 手順

### 1. 何が変わったかを自分の目で確かめる

```
git -C ..\sa-s19 log --oneline main..HEAD
git -C ..\sa-s19 diff --stat main...HEAD
git -C ..\sa-s19 status --short        # 未コミットの取り残しが無いか
```

**diff を実際に読むこと。** コミットメッセージや実装セッションの報告を信用しない。
ラウンド4までに、計画書とコードの食い違いが5件見つかっている。**コードを正とする。**

### 2. コミットの順序を見る（★今回はここが効く）

S19 は「移設を始める前に安全網テストを張る」ことを条件にしてある。
**`git log --oneline main..HEAD` を古い順に読み、テストの追加が移設より前にあること。**
後から足されていたら、それは安全網ではなく後付けの辻褄合わせである。報告すること。

### 3. 受け入れ条件を1つずつ検算する

§3 のプロンプトに番号つきで書いてある。**「満たした」という報告を信じず、自分で確かめる。**
確かめられないものは「確かめられなかった」と報告すること（満たしたことにしない）。

**過去の失敗の型を思い出すこと:**

- **§0.5③「数えた対象がそもそも不完全」** — 「N箇所直した」と書いてあったら、
  **その N の数え方自体を疑う。** grep の網に入らない表記が別にないか自分で引く
  （FU12 は2値で386箇所と数え、短縮表記65箇所を取りこぼしていた）
- **§0.7①「分母が出ていない」** — 棚卸しを求めた条件が満たされていないと、
  **他の条件も検算できなくなる。** S18 は Canvas 150件のうち10件だけ実装したが、
  150 という母数はレビュー側が数えて初めて出た。**分母を先に自分で数えること**
- **§0.7⑤「既存のテストが守っている」という主張** — **そのテストを開いて
  何をアサートしているかまで読むこと。** ファイル名は根拠ではない。
  S17 は「ticker-pages.test.ts が台帳を固定する」と書いたが、実際に固定していたのは
  1銘柄と件数下限の2点だけで、そのテストは main に元からあり1行も足されていなかった
- **FU18 の形** — 受け入れ条件を満たしたまま22節ぶん問題が残り、
  「確認済み」の中に埋もれていた
- **§0.6① の形** — 受け入れ条件が「数値で報告」でも、設計が変わって
  その測定が意味を失うことがある。**条件の文面ではなく意図を見ること**

### 4. 意味の整合を確かめる（★ 無衝突マージを信用しない）

```
git merge-base main feat/panel-registry
git log --oneline "$(git merge-base main feat/panel-registry)..main"
```

分岐後に main へ入った変更が触った**概念**を、作業ブランチ側でも grep すること。
第1波は3件とも無衝突マージだったが、`opengraph-image.tsx` が `range=1y` に
取り残されていた（§0.5①）。**「衝突しなかった」は「整合している」ではない。**

### 5. 今回の固有リスク（★ S19 用。波が変わったらここを書き換える）

**S19 の失敗はすべて「数」で出る。そして全部が無言である。**
IDが消えてもバッジが出なくなるだけ、チャンクが崩れても画面は動く。
したがって**報告の数値を読むのではなく、自分で数え直すこと。**

**① パネルIDの集合が移設前後で完全に同一か**

移設先はレジストリなので `page.tsx` の `id:` を数える方法は使えなくなっている。
**main 側から集合を取り出して、ブランチ側の集合と突き合わせること。**

```
git show main:app/page.tsx > <一時ファイル>     # 移設前の 251件
```

ブランチ側は台帳（レジストリ）から取り出す。**件数だけでなく集合として一致すること。**
1つでも増減・改名があれば共有URL（`?panel=`）と localStorage の開閉状態が壊れる。

**② 安全網テスト自身が弱められていないか（★ここが最大の穴）**

`app/lib/__tests__/page-wiring.test.ts` は **`app/page.tsx` をソースとして読む**設計である。
レジストリ化はIDの所在を動かす作業なので、**このテストは必ず書き換えられる。**
書き換えられた安全網は、黙って緩められる。**diff を読んで、次の3つが残っていること:**

- 全パネルIDが**ちょうど1分類**に属すること（UNAVAILABLE / CAUTION / SAFE）
- 逆向き（台帳にあるのに実在しないID）も検査していること
- 分類の合計が実際のパネル数と一致すること
  （マージ前の main での実測値は **UNAVAILABLE 78 / CAUTION 24 / SAFE 149 = 251**）

**テストが「通った」ことではなく「何を通したか」を見ること。**

**③ FU33 のリテラルID（バッジ）**

`useAnalysisResultSummary("tech-adx", …)` の第1引数が実在IDと一致することを
検査するテストが**移設より前のコミットで**入っていること（→ 手順2）。
現在7箇所。移設後も7箇所あり、全部が台帳のIDと一致することを自分で確かめること。

**★ grep の網に注意。** 実際のコードは引数が改行されている:

```
  useAnalysisResultSummary(
    "tech-adx",
```

`grep 'useAnalysisResultSummary("'` は **0件**を返す。これで「バッジが消えた」と
判断すると誤る（§0.5③ と同じ形）。`grep -A2` か、呼び出し自体を数えること。
マージ前の main での実測は **7件**（ADX / ブレイクアウト / ExtraTechnical /
OBV-VWAP / ストキャス / TechnicalIndicators / VolumeWeightedTech）。

**④ チャンク分割（実測値を報告に頼らない）**

レジストリを「データ」にすると `next/dynamic` の静的解析が効かなくなる可能性がある。
**main とブランチを別々にビルドして、`npm run build` の出力を自分で比較すること。**
「悪化していない」という報告だけを受け取らないこと。

**⑤ FU41 — U2 の仕様が保たれているか**

S17 が `AccordionSection` の React key に `summaryScope` を混ぜている（§0.7③④）。
S19 はこの構造を組み替えるので、**U2 の仕様が変わっていないかを画面で確かめること:**

- 「すべて開く」を押す → **別銘柄を検索 → 一括開放が引き継がれていない**
- 個別に開いたパネルは、銘柄を変えても開いたまま残る
- `sa:open:*` が localStorage に増えるのは**個別に開いたときだけ**

per-panel 購読（FU35）へ寄せたなら、**再マウントが減ったかを報告させること。**

**⑥ FU27 — discretionary 節**

**擬似パネルIDが作られていないこと。** 「AccordionSection 外の節エントリ」として
表現されていること。理由は `app/lib/panel-data-requirements.ts` の冒頭にある。

**⑦ 手順書の同期**

`.claude/skills/add-analysis/SKILL.md` が「配線は5か所」のまま残っていないか。
レジストリ化で減るはずである。**減っていないなら、レジストリが吸収できていない。**
