## 手順

### 1. 何が変わったかを自分の目で確かめる

```
git -C ..\sa-s20 log --oneline main..HEAD
git -C ..\sa-s20 diff --stat main...HEAD
git -C ..\sa-s20 status --short        # 未コミットの取り残しが無いか
```

**diff を実際に読むこと。** コミットメッセージや実装セッションの報告を信用しない。
ラウンド4までに、計画書とコードの食い違いが5件見つかっている。**コードを正とする。**

### 2. コミットの順序を見る（★今回はここが効く）

S20 は「**1コミット目は棚卸し表だけ**（実装を1行も含まない）」を条件にしてある。
**`git log --oneline --reverse main..HEAD` を古い順に読み、
1本目が `docs/canvas-alt-text-inventory.md` だけであること。**
`git show --stat <1本目>` で確かめること。実装が混じっていたら、それは
「先に母数を出す」という条件の骨抜きである（§0.7① の再発）。報告すること。

第4波では、この検査で S19 の安全網テストが**確かに移設より前**にあることを確認できた。
順序は自己申告ではなくログで決まる。

### 3. 受け入れ条件を1つずつ検算する

§3 のプロンプトに番号つきで書いてある。**「満たした」という報告を信じず、自分で確かめる。**
確かめられないものは「確かめられなかった」と報告すること（満たしたことにしない）。

**過去の失敗の型を思い出すこと:**

- **§0.5③「数えた対象がそもそも不完全」** — 「N箇所直した」と書いてあったら、
  **その N の数え方自体を疑う。** grep の網に入らない表記が別にないか自分で引く
  （FU12 は2値で386箇所と数え、短縮表記65箇所を取りこぼしていた）
- **§0.7①「分母が出ていない」** — 棚卸しを求めた条件が満たされていないと、
  **他の条件も検算できなくなる。** S18 は Canvas 150件のうち10件だけ実装したが、
  150 という母数はレビュー側が数えて初めて出た。**分母を先に自分で数えること**
- **§0.7⑤「既存のテストが守っている」という主張** — **そのテストを開いて
  何をアサートしているかまで読むこと。** ファイル名は根拠ではない。
  S17 は「ticker-pages.test.ts が台帳を固定する」と書いたが、実際に固定していたのは
  1銘柄と件数下限の2点だけで、そのテストは main に元からあり1行も足されていなかった
- **FU18 の形** — 受け入れ条件を満たしたまま22節ぶん問題が残り、
  「確認済み」の中に埋もれていた
- **§0.6① の形** — 受け入れ条件が「数値で報告」でも、設計が変わって
  その測定が意味を失うことがある。**条件の文面ではなく意図を見ること**

### 4. 意味の整合を確かめる（★ 無衝突マージを信用しない）

```
git merge-base main feat/canvas-alt-text-rest
git log --oneline "$(git merge-base main feat/canvas-alt-text-rest)..main"
```

分岐後に main へ入った変更が触った**概念**を、作業ブランチ側でも grep すること。
第1波は3件とも無衝突マージだったが、`opengraph-image.tsx` が `range=1y` に
取り残されていた（§0.5①）。**「衝突しなかった」は「整合している」ではない。**

### 5. 今回の固有リスク（★ S21 用。波が変わったらここを書き換える）

**S21 の失敗は「テストを足したが、そのテストが何も守っていない」形で出る。**
§0.7⑤ の教訓がそのまま当てはまる——S17 は「既存テストが守っている」と書いたが、
実際に固定していたのは2点だけで、本体の問題（台帳が腐る）は未解決だった。
**ファイル名は根拠ではない。テストを開いて何をアサートしているか読むこと。**

**① 追加されたテストを実際に落としてみたか（★ここが最重要）**

3件とも「ずれても画面が壊れない」種類なので、**テストが本当にずれを捕まえるかは
壊してみないと分からない。** レビュー側で次を実際にやること:

```
# FU43: 無料IDを1つ改名して落ちるか
# FU28: TICKER_PAGE_INSTRUMENTS に未収録文字を含む銘柄を1件足して落ちるか
# → どちらも npm test が落ちること。落ちなければテストは何も守っていない
```

**直したら必ず元へ戻すこと。** 戻し忘れると main に混入する。

**② 「拾えた件数 >= N」の生存確認があるか（★受け入れ条件5）**

`a6fec7c`（S19）が手本。走査が0件でも「全部通った」と報告してしまう形を塞ぐ。
**新しいテストのそれぞれについて確認すること。** 1本でも欠けていたら指摘する。

**③ FU43 — 課金境界を動かしていないか**

`FREE_PANEL_IDS` の**8件は現状維持**である（§6.4「既に無料で公開しているものを
有料側に移さない」）。テストは現状を固定するために書くのであって、
**分類を見直す作業ではない。** 8件の無料判定が1つでも変わっていたら差し戻し。

```
git diff main..HEAD -- app/lib/tiers.ts   # FREE_PANEL_IDS の中身が動いていないこと
```

レジストリ側に `free: true` を足す設計変更を選んだ場合は、
**`isPanelFree()` の入出力が全パネルで一致すること**を自分で確かめること
（S19 が251件を1件ずつ突き合わせたのと同じ形）。

**④ FU40 — 「見送り」で閉じていてもよい**

`/t/[ticker]` は取得失敗時に `noindex, follow` の代替表示へ落ちる。
**落ちた先が無害なら台帳そのものを廃止できる**——これを検討した形跡があるか。

外部取得を増やす解になっていたら**差し戻し**（S17 の FU20 判断を覆さない）。
逆に「検知できないので見送り」でも受け入れてよい。§9 の
「**Null result を『でも実はこう使えます』と救済しない**」に沿う側である。
**その場合は理由と復活条件がコードのコメントに残っていること。**

**⑤ FU28 — フォント資産を動かしていないか**

`_fonts/OFL.txt` は OFL の再配布条件を満たすために同じディレクトリに置いてある。
**移動・削除していたらライセンス違反である。**

```
git diff --name-status main..HEAD -- 'app/t/[ticker]/_fonts/'
```

`.ttf` と `subset-base64.ts` が変わっているなら、**なぜ焼き直す必要があったのか**を
確かめること（現在の98銘柄では被覆できているはずで、焼き直しは不要のはず）。

**⑥ パネルIDが1つも変わっていないか（★受け入れ条件7）**

```
diff <(git show main:app/lib/panel-registry.tsx | grep -o 'id: "[^"]*"' | sort) \
     <(grep -o 'id: "[^"]*"' app/lib/panel-registry.tsx | sort)
```

差分が出たら**共有URL `?panel=` と `sa:open:<id>` が壊れる**（§6.5）。

**⑦ lint の警告数が着手前と同じか**

着手前の値を**自分で測ること**（`git checkout <merge-base> -- app` → lint →
`git checkout HEAD -- app`。作業ツリーが clean なことを先に確認）。
S20 では総数だけでなく**ルール構成とファイル集合まで一致**することを確認した。
同じ強さで見ること。

**⑧ この波は画面をほとんど変えない**

`app/components/analysis/` に用は無いはずである。触れていたら理由を確かめること。
ただし **OG画像だけは実際に開いて見ること**——`/t/7203` で日本語が豆腐に
なっていないか、数値の入ったカードが出ているか。**FU28 の壊れ方は「静かな退化」で、
テストが通っても画像が汎用に落ちている可能性がある。**


### 6. 検証を走らせる

```
# worktree で
npm test        # 100件（マージ前の main での実測。増減を報告すること）
npm run lint    # 0エラー / 272警告（増減があれば報告）
npm run build

# マージ後の main でも、もう一度
npm test; npm run lint; npm run build
npm start       # ★ dev ではなく本番ビルドで、変更した画面を実際に開くこと
```

**テストが落ちたら、直す前に「実装とテストのどちらが正しいか」を報告すること。**

### 7. ここで一度止まって報告する（★勝手にマージしない）

- **秒の実測**（重い節で「すべて開く」→ 期間変更。main と作業ブランチの両方）
- 検証の結果（test / lint / build の数値）
- **マージしてよいか、直してから入れるべきか**の推奨

**オーナーの承認を得てから 8 へ進むこと。**
