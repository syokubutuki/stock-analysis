## 手順

### 1. 何が変わったかを自分の目で確かめる
各ブランチについて:

```
git -C ..\sa-s17 log --oneline main..HEAD
git -C ..\sa-s17 diff --stat main...HEAD
git -C ..\sa-s17 status --short        # 未コミットの取り残しが無いか
```

**diff を実際に読むこと。** コミットメッセージや実装セッションの報告を信用しない。
ラウンド4までに、計画書とコードの食い違いが5件見つかっている。**コードを正とする。**

S17 と S18 は編集してよいファイルを分けてある。**diff のファイル一覧で検算すること。**

線を越えていたら、**越えた理由と、もう片方の変更と衝突しないかを報告すること。**

### 3. 受け入れ条件を1つずつ検算する
§3 のプロンプトに番号つきで書いてある。**「満たした」という報告を信じず、自分で確かめる。**
確かめられないものは「確かめられなかった」と報告すること（満たしたことにしない）。

**過去の失敗の型を思い出すこと:**
- **§0.5③「数えた対象がそもそも不完全」** — 「N箇所直した」と書いてあったら、
  **その N の数え方自体を疑う。** grep の網に入らない表記が別にないか自分で引く
  （FU12 は2値で386箇所と数え、短縮表記65箇所を取りこぼしていた）
- **FU18 の形** — 受け入れ条件を満たしたまま22節ぶん問題が残り、
  「確認済み」の中に埋もれていた
- **§0.6① の形** — 受け入れ条件が「数値で報告」でも、設計が変わって
  その測定が意味を失うことがある。**条件の文面ではなく意図を見ること**

### 4. 意味の整合を確かめる（★ 無衝突マージを信用しない）
```
git merge-base main feat/panel-followups
git log --oneline "$(git merge-base main feat/panel-followups)..main"
```
分岐後に main へ入った変更が触った**概念**を、作業ブランチ側でも grep すること。
第1波は3件とも無衝突マージだったが、`opengraph-image.tsx` が `range=1y` に
取り残されていた（§0.5①）。**「衝突しなかった」は「整合している」ではない。**

### 5. S17 と S18 の相互作用を見る（★今回の固有リスク）
2本が別々の main から切られている。互いの変更が噛み合うかを確かめること。

- **1本目をマージした後、2本目を必ず再検証する。**
  `git merge-tree` で無衝突でも、2本目のテスト・ビルドを通し直すこと
- **FU26 × S15 のバッジ**: S17 が `tech-adx` / `tech-breakout` / `tech-stoch` を
  UNAVAILABLE に倒したら、**S15 が付けたバッジも消えるはず**（`AccordionSection` が
